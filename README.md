# NixOS Configuration

This repository contains my complete NixOS configuration, including system configuration, Home Manager configuration, desktop environment, applications, development tools, shell configuration, Neovim, and other user-specific settings.

The configuration is managed declaratively with **Nix flakes** and **Home Manager**. The goal is to keep the entire system configuration reproducible, modular, version-controlled, and easy to restore on a new installation.

This repository is primarily my personal configuration, but the structure is intentionally modular enough to be used as a starting point for your own NixOS setup.

> **Important:** This configuration is hardware- and user-specific. Do not copy it blindly onto another machine. In particular, `hardware-configuration.nix`, usernames, home directories, host names, and some application settings need to be adapted.

---

## Overview

The repository is based on a NixOS flake and currently defines a single NixOS host:

```text
nix-btw
```

The configuration uses:

* NixOS
* Nix flakes
* `nixpkgs`
* Home Manager
* NixVim
* Nixcord
* modular Nix files
* declarative system packages
* declarative user packages
* declarative shell configuration
* declarative desktop configuration

The main entry point is:

```text
flake.nix
```

The flake defines the NixOS system and connects the system configuration with Home Manager.

# Repository Structure

The repository currently has the following high-level structure:

```text
.
├── nix/
├── sys-nix/
├── configuration.nix
├── hardware-configuration.nix
├── home.nix
├── flake.nix
├── flake.lock
└── README.md
```

Each part has a different purpose.

---

## `flake.nix`

`flake.nix` is the entry point of the entire configuration.

It defines the external dependencies used by the system and exposes the actual NixOS configuration.

The current flake uses:

```nix
nixpkgs
home-manager
nixcord
nixvim
```

The main NixOS configuration is exposed as:

```text
nixosConfigurations.nix-btw
```

The architecture is approximately:

```text
flake.nix
    │
    ├── nixpkgs
    ├── home-manager
    ├── nixcord
    └── nixvim
          │
          ▼
    NixOS configuration
          │
          ├── configuration.nix
          │      │
          │      ├── hardware-configuration.nix
          │      └── sys-nix/
          │
          └── home.nix
                 │
                 └── nix/
```

The important part of the flake is the connection between NixOS and Home Manager.

Home Manager is loaded as a NixOS module rather than being maintained as a completely separate configuration.

This means that rebuilding the NixOS system also applies the Home Manager configuration.

---

# `configuration.nix`

`configuration.nix` is intentionally kept very small.

It currently imports:

```nix
./hardware-configuration.nix
./sys-nix/defaults.nix
```

This means that the file acts primarily as the entry point for the system-level configuration.

Instead of putting hundreds of options into one enormous `configuration.nix`, the actual configuration is separated into modules inside `sys-nix/`.

This makes individual parts of the system easier to find and modify.

The basic structure is:

```text
configuration.nix
    │
    ├── hardware-configuration.nix
    │
    └── sys-nix/
          └── defaults.nix
```

---

# `hardware-configuration.nix`

`hardware-configuration.nix` is the hardware-specific part of the configuration.

It is normally generated by NixOS during installation with:

```bash
nixos-generate-config
```

This file describes things such as:

* filesystems
* disk partitions
* mount points
* boot-related hardware configuration
* detected kernel modules
* hardware-specific settings

Because this configuration belongs to a specific machine, **you should normally generate your own version instead of copying mine**.

On a new NixOS installation, you can generate it with:

```bash
sudo nixos-generate-config
```

The generated file will normally be placed in:

```text
/etc/nixos/hardware-configuration.nix
```

You can then copy the generated file into your cloned repository.

For example:

```bash
cp /etc/nixos/hardware-configuration.nix ~/NixOS/
```

The exact location of the repository does not matter as long as the relative import in `configuration.nix` remains correct.

---

# `sys-nix/`

The `sys-nix` directory contains the system-level configuration.

This is where functionality that belongs to the operating system itself should live.

The directory is separated from `configuration.nix` so that the main configuration stays readable and individual components can be modified independently.

The general idea is:

```text
sys-nix/
├── defaults.nix
└── ...
```

`defaults.nix` acts as the central entry point for these system modules.

Instead of maintaining one huge NixOS configuration file, individual parts can be organized into separate files and imported from this directory.

This is especially useful once the configuration grows beyond a basic NixOS installation.

---

# `nix/`

The `nix/` directory contains the modular user-side configuration.

It is imported by:

```text
home.nix
```

through:

```nix
./nix/imports.nix
```

This directory is intended to contain reusable and logically separated configuration components.

For example, configuration that belongs specifically to the user environment can be separated from the operating-system configuration.

This makes the distinction between:

```text
system configuration
```

and:

```text
user environment
```

much clearer.

---

# `home.nix`

`home.nix` is the Home Manager configuration.

It defines the user environment rather than the operating system itself.

Among other things, it contains:

* the Home Manager user
* the user's home directory
* Git configuration
* shell configuration
* aliases
* environment variables
* Home Manager settings

The current configuration uses:

```nix
home.username = "raphael";
home.homeDirectory = "/home/raphael";
```

These values are **machine/user specific**.

If you use this repository as a template, you must change them.

For example:

```nix
home.username = "alice";
home.homeDirectory = "/home/alice";
```

The same applies to user-specific Git information.

---

# `flake.lock`

`flake.lock` locks the exact versions of the flake inputs.

This is an important part of reproducibility.

For example, `flake.nix` may say:

```text
nixpkgs = nixos-unstable
```

but the lock file records the exact revision that was used.

This means two systems using the same repository can build against the same dependency revisions.

You normally **should commit `flake.lock` to Git**.

To update all flake inputs:

```bash
nix flake update
```

After updating, test the configuration before rebooting.

Do not directly deploy the repository unchanged.

Instead:

1. Install NixOS normally.
2. Generate your hardware configuration.
3. Clone this repository.

# Fresh NixOS Installation

After installing NixOS, make sure flakes are available.

You can check:

```bash
nix --version
```

and:

```bash
nix flake --help
```

If flakes are not enabled, enable the required experimental features.

A common configuration is:

```nix
experimental-features = nix-command flakes
```

in:

```text
/etc/nix/nix.conf
```

After changing the configuration, restart the Nix daemon if necessary.

# Clone the Repository

Clone the repository somewhere in your home directory:

```bash
git clone https://github.com/rhantschk-cmyk/NixOS.git ~/NixOS
```

Then enter it:

```bash
cd ~/NixOS
```

# Generate Your Hardware Configuration

Do not use the existing `hardware-configuration.nix` on another computer.

Generate your own:

```bash
sudo nixos-generate-config
```

This normally creates:

```text
/etc/nixos/configuration.nix
/etc/nixos/hardware-configuration.nix
```

Copy the hardware configuration into the repository:

```bash
cp /etc/nixos/hardware-configuration.nix ~/NixOS/hardware-configuration.nix
```

You can then inspect it:

```bash
nvim ~/NixOS/hardware-configuration.nix
```

This is especially important when installing on a computer with different:

* disks
* partitions
* filesystems
* CPU
* GPU
* boot configuration
* hardware devices

# Configure Your User

Open:

```text
home.nix
```

and change:

```nix
home.username = "raphael";
home.homeDirectory = "/home/raphael";
```

to your own user.

For example:

```nix
home.username = "alice";
home.homeDirectory = "/home/alice";
```

Also change user-specific Git configuration:

```nix
programs.git = {
  enable = true;

  settings.user = {
    name = "Your Name";
    email = "you@example.com";
  };
};
```

Do not leave personal information from this repository in your own configuration.

---

# Configure the Host

The flake currently defines:

```nix
nixosConfigurations.nix-btw
```

If your machine has a different name, you can change this.

For example:

```nix
nixosConfigurations.my-pc = nixpkgs.lib.nixosSystem {
```

The resulting configuration can then be built using:

```bash
sudo nixos-rebuild switch --flake .#my-pc
```

The name after `#` must exactly match the name defined inside `nixosConfigurations`.

---

# Applying the Configuration

Before applying a new configuration, it is a good idea to build it first.

From the repository:

```bash
cd ~/NixOS
```

Build the configuration:

```bash
nixos-rebuild build --flake .#nix-btw
```

Replace `nix-btw` with your own host name if you changed it.

If the build succeeds, switch to the new configuration:

```bash
sudo nixos-rebuild switch --flake .#nix-btw
```

After the switch completes, the new configuration is active.

---

# Booting Into a New Configuration

Instead of immediately switching, you can also prepare a configuration for the next boot:

```bash
sudo nixos-rebuild boot --flake .#nix-btw
```

This is useful when you want to test a new system generation without immediately replacing the currently running configuration.

After rebooting, NixOS will boot into the new generation.

---

# Testing Before Switching

A useful workflow is:

```bash
nix flake check
```

followed by:

```bash
sudo nixos-rebuild build --flake .#nix-btw
```

and only after a successful build:

```bash
sudo nixos-rebuild switch --flake .#nix-btw
```

This gives you an opportunity to catch evaluation and build errors before changing the running system.

---

# Understanding NixOS Generations

One of the advantages of this setup is that every successful NixOS rebuild creates a new system generation.

If a new configuration causes problems, you can select an older generation from the bootloader.

You can also inspect existing generations with:

```bash
sudo nix-env --list-generations --profile /nix/var/nix/profiles/system
```

This is one of the reasons it is useful to keep the configuration declarative instead of manually modifying files throughout the system.

---

# Updating the System

The repository uses a flake lock file, so updates are controlled through the flake.

To update all inputs:

```bash
nix flake update
```

Then inspect the changes:

```bash
git diff
```

You can test the updated configuration:

```bash
nix flake check
```

and:

```bash
sudo nixos-rebuild build --flake .#nix-btw
```

If everything works as expected:

```bash
sudo nixos-rebuild switch --flake .#nix-btw
```

Finally commit the updated lock file:

```bash
git add flake.lock
git commit -m "Update flake inputs"
```

# Why This Structure?

A traditional NixOS configuration often starts as:

```text
configuration.nix
hardware-configuration.nix
```

This works well for small systems.

However, as more software and configuration gets added, `configuration.nix` can become very large.

Instead of having one file containing everything, this repository separates configuration into logical components.

Conceptually:

```text
NixOS
│
├── System
│   └── sys-nix/
│
├── Hardware
│   └── hardware-configuration.nix
│
├── User
│   └── home.nix
│
└── User modules
    └── nix/
```

This makes it possible to modify one part of the system without having to navigate a huge monolithic file.

---

# Home Manager

Home Manager is used to declaratively manage the user environment.

Instead of manually configuring files under:

```text
~/.config/
~/.local/
```

and installing applications individually, configuration can be declared in Nix.

The result is that the user environment can be recreated together with the operating system.

In this repository, Home Manager is integrated directly into the NixOS flake.

Therefore, you normally do **not** need to run a separate:

```bash
home-manager switch
```

for this configuration.

The Home Manager configuration is applied as part of:

```bash
sudo nixos-rebuild switch --flake .#nix-btw
```

---

# NixVim

The repository also includes NixVim as a flake input.

This allows the Neovim configuration to be managed declaratively through Nix rather than relying on an independently managed plugin installation.

The advantage is that the editor configuration becomes part of the same reproducible system configuration.

If you want to use your own Neovim configuration, you can modify or remove the relevant NixVim configuration instead of manually installing the editor configuration outside of Nix.

---

# Nixcord

The flake also includes:

```text
nixcord
```

as an input.

This allows Discord configuration to be managed declaratively.

If you do not use Discord or do not need this integration, you can remove the corresponding flake input and configuration.

# Git and Version Control

Because this repository represents the configuration of an entire operating system, Git becomes particularly useful.

A typical change should look like:

```bash
git status
```

then:

```bash
git diff
```

After verifying the change:

```bash
git add .
git commit -m "Describe the change"
```

and finally:

```bash
git push
```

This gives you a complete history of your system configuration.

If a change breaks something, you can inspect previous commits and restore an earlier configuration.

---

# Keeping Secrets Out of the Repository

This repository is public.

Therefore, **never commit secrets**.

Do not put things such as:

* passwords
* API keys
* private SSH keys
* authentication tokens
* recovery codes
* private certificates
* personal access tokens
* `.env` files containing secrets

into the repository.

Before pushing a change, check:

```bash
git diff
```

and:

```bash
git status
```

Remember that deleting a secret from the latest commit does not necessarily remove it from Git history.

If this repository is used for secrets management in the future, use an encryption system such as `sops`/`age` rather than storing plaintext secrets.

# Troubleshooting

## The flake cannot be evaluated

Try:

```bash
nix flake check
```

This usually provides a more useful error message than immediately running a system rebuild.

Also make sure you are inside the repository:

```bash
cd ~/NixOS
```

and that the repository contains:

```text
flake.nix
flake.lock
```

---

## The host does not exist

If you get an error similar to:

```text
does not provide attribute 'nixosConfigurations.some-host'
```

check the names inside:

```text
flake.nix
```

For example, if the flake contains:

```nix
nixosConfigurations.nix-btw = ...
```

the rebuild command must use:

```bash
sudo nixos-rebuild switch --flake .#nix-btw
```

not:

```bash
sudo nixos-rebuild switch --flake .#my-pc
```

unless you actually renamed the configuration.

---

## Hardware configuration errors

If you are using this repository on another computer, make sure you generated a new:

```text
hardware-configuration.nix
```

Do not assume the hardware configuration from another machine will work correctly.

---

## Home Manager errors

Check:

```text
home.nix
```

for user-specific paths.

Especially verify:

```nix
home.username
home.homeDirectory
```

Also check whether any configuration assumes software or directories that do not exist on your machine.

# Reproducibility

The main reason for keeping a NixOS configuration like this in Git is reproducibility.

Instead of documenting a system as:

```text
Install Firefox
Install Neovim
Configure Git
Install these packages
Change this config file
Install this plugin
Change this environment variable
...
```

the desired state is described in Nix.

Conceptually:

```text
Git repository
      │
      ▼
   flake.nix
      │
      ├── system configuration
      ├── hardware configuration
      ├── Home Manager
      ├── applications
      ├── shell
      ├── editor
      └── desktop
      │
      ▼
   NixOS system
```

A new machine can therefore be brought much closer to the existing system without manually reproducing every configuration step.

# Philosophy

This repository follows a simple principle:

> If it can reasonably be described declaratively, it should be part of the configuration.

The goal is not to make the configuration unnecessarily complicated. The goal is to avoid having important parts of the system exist only as undocumented manual changes.

The configuration is therefore split into modules where appropriate while keeping `flake.nix`, `configuration.nix`, and `home.nix` as understandable entry points.

The result is a system that can be:

* version controlled
* reviewed with Git
* reproduced
* rolled back
* modified declaratively
* transferred to another machine
* rebuilt after a fresh installation
